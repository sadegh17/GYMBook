# GYMBook — برنامه‌های شخصی کاربر (User-Defined Programs)

تاریخ: ۲۰۲۶-۰۹-۱۵ · وضعیت: پیش‌نویس برای بازبینی

## ۱. هدف

در نسخه فعلی، فقط **ادمین** برنامه می‌سازد و هر کاربر دقیقاً **یک** برنامه فعال
(`profiles.program_id`) دارد. بخش‌ها (`warm`/`main`/`cool`) ثابت‌اند و حذف برنامه،
لاگ‌هایش را هم با `on delete cascade` پاک می‌کند.

هدف این فیچر: هر کاربر بتواند **برنامه تمرینی خودش** را بسازد:

- روزهای هفته‌ای که می‌خواهد تمرین کند را انتخاب کند
- به برنامه اسم بدهد
- به هر روز یک عنوان اختصاصی بدهد
- از بانک حرکات، حرکت‌های هر روز را انتخاب کند
- حرکت‌های هر روز را با **نام دلخواه** دسته‌بندی کند (مثلاً «گرم‌کردن»، «بخش اصلی»)
- تعداد ست و تکرار هر حرکت را تنظیم کند و ذخیره کند
- حداکثر **۳ برنامه** داشته باشد (بیشتر از آن باید یکی را حذف کند)
- کالری هر حرکت با توجه به مشخصات کاربر (وزن) و ست/تکرار حساب شود
- در صفحه «امروز» برنامه موردنظر را انتخاب کند
- یک برنامه را به‌عنوان **پیش‌فرض** ست کند
- لاگ حرکات بر اساس برنامه ذخیره شود و **با حذف برنامه، لاگ‌ها باقی بمانند** و در گزارش دیده شوند

## ۲. تصمیمات کلیدی (تأییدشده توسط مالک)

1. **حذف نرم (soft delete):** حذف برنامه = `is_deleted=true`. روزها/بخش‌ها/حرکات/لاگ‌ها
   در دیتابیس **می‌مانند**؛ برنامه از انتخاب‌گر و شمارنده ۳تایی پنهان می‌شود؛ لاگ‌ها در
   گزارش کامل قابل مشاهده‌اند. (به‌جای حذف سخت + اسنپ‌شات.)
2. **درصد تکمیل روز = همه بخش‌ها:** با حذف نام‌های ثابت بخش، «درصد انجام‌شده روز» روی
   **تمام** حرکت‌های آن روز حساب می‌شود (بدون تفکیک warm/main/cool).
3. **انتخاب‌گر «امروز»: برنامه‌های خودش + برنامه ادمین.** کاربر هم برنامه‌های شخصی‌اش
   و هم برنامه‌ای که ادمین به او اختصاص داده را می‌تواند انتخاب کند.
4. **سقف ۳ همه با هم:** شمارنده ۳تایی شامل برنامه‌های شخصی کاربر **و** برنامه(های)
   اختصاص‌یافته ادمین به او می‌شود.

## ۳. مدل داده (مایگریشن `0002_user_programs.sql`)

### ۳.۱ `programs` — تغییرات
| ستون جدید | نوع | توضیح |
|---|---|---|
| owner_id | uuid FK→profiles nullable | `null` = برنامه سراسری/ادمین؛ مقدار = برنامه شخصی کاربر |
| is_deleted | boolean not null default false | حذف نرم؛ `true` از همه‌جا پنهان |

- برنامه‌های موجود (سراسری) `owner_id=null` می‌مانند.
- `created_by` موجود دست‌نخورده (برای رد‌اثر).

### ۳.۲ `program_sections` — جدول جدید (دسته‌های با نام دلخواه)
| ستون | نوع | توضیح |
|---|---|---|
| id | uuid PK | |
| day_id | uuid FK→program_days on delete cascade | |
| name | text not null | نام دلخواه دسته، مثل «گرم‌کردن»، «بخش اصلی» |
| sort | int not null default 0 | ترتیب نمایش دسته‌ها |

### ۳.۳ `program_items` — تغییر
- ستون `section` (enum `warm/main/cool`) **حذف** و `section_id` (uuid FK→program_sections
  on delete cascade) **جایگزین** می‌شود.
- `sets`, `reps`, `rest_sec`, `sort` بدون تغییر.

### ۳.۴ `program_days` — بدون تغییر ساختاری
- `day_key` همچنان یکی از `sat..fri`؛ فقط روزهایی که کاربر انتخاب می‌کند سطر می‌گیرند.
- `title` = عنوان اختصاصی روز (همین الان وجود دارد). `day_label` برای نام روز هفته.
- **قید یکتایی** `unique(program_id, day_key)` حفظ می‌شود.

### ۳.۵ `checks` — تغییر برای ماندگاری لاگ
| تغییر | توضیح |
|---|---|
| `item_id`: `on delete cascade` → **`on delete set null`** | حذف فیزیکی یک آیتم، لاگش را پاک نکند |
| ستون جدید `exercise_name text` | اسنپ‌شات نام حرکت لحظهٔ تیک |
| ستون جدید `sets int` | اسنپ‌شات تعداد ست لحظهٔ تیک |

`kcal` و `date/day_key/user_id` بدون تغییر. با حذف نرمِ کل برنامه، هیچ `item_id` نمی‌شکند؛
این اسنپ‌شات فقط برای حذف **تکیِ یک حرکت** داخل برنامه در حال ویرایش لازم است (بند ۶).


### ۳.۶ مهاجرت داده (نگاشت داده موجود)
- سه `program_items.section → سه ردیف `program_sections` به‌ازای هر روز:
  `warm→«گرم‌کردن»`, `main→«تمرین اصلی»`, `cool→«سردکردن»` (با همان ترتیب) و اتصال
  `section_id` هر آیتم. سپس حذف ستون `section`.
- ستون‌های جدید روی ردیف‌های موجود: `is_deleted=false`, `owner_id=null`.

## ۴. سقف ۳ برنامه (اجرا در دیتابیس)

تریگر `before insert on programs`:
- فقط وقتی `NEW.owner_id` مقدار دارد (برنامه شخصی) شمارش می‌شود.
- شمارش = تعداد برنامه‌هایی که برای این کاربر «فعال و در دسترس»اند و `is_deleted=false`:
  ۱) برنامه‌های شخصی‌اش (`owner_id = NEW.owner_id`) + ۲) برنامه(های) سراسری که
  `profiles.program_id` او به آن‌ها اشاره می‌کند.
- اگر `≥ 3` باشد: `raise exception` با پیام فارسیِ قابل‌نمایش.
- سقف برای **ادمین** اعمال نمی‌شود (برنامه‌های سراسری `owner_id=null` شمارش نمی‌شوند).

پیام خطا در UI (ساخت برنامه) به‌صورت بنر قرمز نشان داده می‌شود:
«می‌توانید حداکثر ۳ برنامه داشته باشید. برای ساخت برنامه جدید، یکی را حذف کنید.»

> تریگر فقط `on insert` می‌دود؛ اگر ادمین بعد از ۳ برنامهٔ شخصی، برنامه سراسری هم
> اختصاص دهد، حالت موجود retroactively مسدود نمی‌شود — فقط ساختِ بعدی تا زیر سقف ۳ نیامده
> رد می‌شود. این رفتار عمدی و قابل‌قبول است.

## ۵. احراز هویت و RLS

اصل: کاربر روی برنامه‌های **شخصیِ خودش** کامل CRUD می‌کند؛ برنامه‌های سراسری فقط
خواندنی‌اند.

- `programs`
  - select: `is_deleted=false and (owner_id is null or owner_id = auth.uid() or is_admin())`
  - insert: `owner_id = auth.uid() or is_admin()`  *(سقف ۳ با تریگر)*
  - update: `owner_id = auth.uid() or is_admin()`
  - delete: اجازه نمی‌دهیم (حذف = update روی `is_deleted`)؛ فقط ادمین delete سخت
- `program_sections` / `program_days` / `program_items`
  - write فقط برای روز/برنامه‌ای که `owner_id = auth.uid()` یا ادمین:
    با `exists (select 1 from program_days d join programs p on p.id=d.program_id
    where d.id = <day_id> and (p.owner_id = auth.uid() or is_admin()))`
  - select: برای همه کاربرانِ لاگین‌شده (تا برنامه ادمین قابل دیدن باشد)
- `profiles`
  - سیاست «self update» فعلی `program_id` را **قفل** می‌کند. باید شل شود تا کاربر
    بتواند برنامه پیش‌فرض/منتخب خودش را عوض کند، **اما** فقط به برنامه‌ای که
    `owner_id = auth.uid()` یا `owner_id is null` است (جلوگیری از اشاره به برنامهٔ دیگران).
- `checks`: بدون تغییر (own insert/select/delete).

`is_deleted=true` روی برنامه‌ای که به‌عنوان `profiles.program_id` انتخاب شده مجاز نیست
(UI قبل از حذف اگر پیش‌فرض باشد، کاربر را به انتخاب برنامه دیگر وادار می‌کند).

## ۶. جریان حذف

- «حذف برنامه» (دکمه کاربر) → `update programs set is_deleted=true where id=? and owner_id=auth.uid()`.
- روزها/بخش‌ها/آیتم‌ها/`checks` دست‌نخورده می‌مانند → تاریخچه و گزارش کامل باقی می‌ماند.
- اگر کاربر **یک حرکت را از روزِ در حال ویرایش** حذف کند و آن حرکت لاگ داشته باشد:
  برای حفظ لاگ، آیتم حذف فیزیکی **نمی‌شود**؛ اگر `checks` دارد، UI هشدار می‌دهد و
  در صورت تأیید، آیتم حذف می‌شود و `checks` با `item_id` شکسته (orphans) می‌ماند.
  برای اینکه گزارش نشکن، `checks.item_id` از `on delete cascade` به **`on delete set null`**
  تغییر می‌کند و گزارش تاریخچه (بند ۹) به `item_id is null` هم نام حرکت را نشان می‌دهد
  (از `checks` بیرون آیتم در دسترس نیست → **اسنپ‌شات نام حرکت و ست روی خود `checks`**؛
  ببند ۹). این فقط برای حذف تکیِ آیتم است؛ حذف کل برنامه soft است و هیچ لاگی نمی‌شکند.

## ۷. صفحات و مسیرها

| مسیر | محتوا | دسترسی |
|---|---|---|
| `/programs` | «برنامه‌های من»: کارت برنامه‌ها (اسلات «X از ۳»)، ساخت، حذف نرم، ستارهٔ پیش‌فرض، سازندهٔ برنامه | کاربر لاگین‌شده (مجاور `Today`/`Report`/`Profile` در نوار ناوبری) |
| `/` (امروز) | افزودن **انتخاب‌گر برنامه** بالای `DayNav` + رندر بخش‌های داینامیک | کاربر لاگین‌شده |
| `/admin/programs` | همان سازنده، به‌عنوان برنامه سراسری (`owner_id=null`) | ادمین |

### ۷.۱ سازندهٔ برنامه مشترک (کامپوننت)
منطق ساخت/ویرایش برنامه (انتخاب روزها ← عنوان روز ← دسته‌های دلخواه ← افزودن حرکت از
بانک با ست/تکرار/استراحت ← حذف/جابجایی) در یک کامپوننت مشترک
`ProgramBuilder` می‌نشیند؛ هر دو صفحهٔ `/programs` و `/admin/programs` از آن استفاده
می‌کنند (فرق: `owner_id` مقدار کاربر جاری یا `null`). این از دو برابر شدن کد جلوگیری
می‌کند.

### ۷.۲ گام‌های ساخت برنامه در UI
1. **اسم برنامه** + انتخاب **روزهای هفته** (چک‌باکس شنبه…جمعه).
2. برای هر روز انتخاب‌شده: **عنوان اختصاصی**.
3. ساخت **دسته‌ها** با نام دلخواه (پیش‌فرض «بخش ۱»؛ کاربر عوض می‌کند).
4. در هر دسته: **افزودن حرکت از بانک** + تنظیم **ست/تکرار/استراحت** + **پیش‌نمایش `≈kcal`**.
5. **ذخیره** (هر تغییر، یک فراخوان مستقل Supabase + `invalidate`؛ همان الگوی
   `Programs.jsx` فعلی، بدون نوشتن خوش‌بینانه برای حفظ یکپارچگی `sort`).

## ۸. پیش‌فرض و انتخاب‌گر «امروز»

- **پیش‌فرض** = `profiles.program_id` (همان ستون فعلی؛ معنایش «برنامه پیش‌فرض/فعال» می‌شود).
  در صفحهٔ `/programs` هر برنامهٔ کاربر یک دکمهٔ ستاره دارد: `update profiles set program_id=?`.
- **انتخاب‌گر امروز:** بالای `DayNav` یک `select` نشان می‌دهد: [برنامه‌های شخصی کاربر
  با `is_deleted=false`] + [برنامه ادمین/سراسریِ `program_id`] + برچسب «پیش‌فرض» روی
  `program_id`. انتخاب برنامه‌ای که **پیش‌فرض نیست** موقتی است (state محلیِ صفحه؛ دیتابیس
  عوض نمی‌شود). اگر برنامه‌ای که انتخاب شده هیچ `program_days` برای امروز نداشته باشد،
  همان روز اول هفتهٔ برنامه نمایش داده می‌شود (رفتار `todayDefaultIndex` حفظ/تعمیم).

## ۹. کالری و گزارش

- **کالری:** بدون تغییر فرمول — `calcKcal(exercise, item, weightKg)` (MET×۳.۵×وزن÷۲۰۰
  × زمان خالص کار). فقط **پیش‌نمایش `≈kcal`** در سازنده اضافه می‌شود تا هنگام ساخت، هزینهٔ
  هر حرکت با وزن کاربر دیده شود.
- **`v_day_progress` (بازنویسی):** `main_done`/`main_total` به `total_done`/`total_items`
  تغییر می‌کند که **روی همهٔ آیتم‌های روز** حساب می‌شوند (بدون فیلتر `section='main'`، چون
  بخش ثابت حذف شد). گروه‌بندی `user_id,date,day_key` حفظ می‌شود. اگر کاربر در یک روز بین
  دو برنامه جابه‌جا شده باشد، `count(*)` روی `checks` آن روز همهٔ تیک‌ها را می‌شمارد
  (قابل قبول: گزارش «چقدر کار کردم» است نه «درصد کدام برنامه»).
- **اسنپ‌شات برای ماندگاری لاگ:** برای اینکه لاگ حتی بعد از حذف تکیِ آیتم هم در تاریخچه
  دیده شود، `checks` دو ستون اضافه می‌کند: `exercise_name text` و `sets int` که لحظهٔ
  تیک‌زدن از حرکت کپی می‌شوند. `ExerciseHistory` و تاریخچهٔ حرکت، `checks.item_id` را
  `on delete set null` می‌کنند و برای نمایش از این اسنپ‌شات استفاده می‌کنند (fallback به
  جوینِ زنده اگر `item_id` هنوز معتبر باشد).

## ۱۰. تست

- **Vitest منطقی:** نگاشت مهاجرت `section→program_sections`؛ شمارش سقف ۳ (مرز ۲/۳/۴،
  با احتساب برنامه ادمین)؛ `v_day_progress` روی «همهٔ بخش‌ها»؛ حفظ `calcKcal`.
- **سطح کامپوننت:** `ProgramBuilder` (ساخت روز/دسته/آیتم)، انتخاب‌گر برنامه در Today،
  دکمهٔ ستارهٔ پیش‌فرض، بنر خطای سقف ۳.
- **RLS:** کوئری mock با JWT دو نقش: member نمی‌تواند برنامه/روز/آیتم کاربر دیگر را
  ویرایش کند؛ می‌تواند برنامه خودش را بسازد/حذف نرم کند؛ `program_id` فقط به برنامهٔ
  قابل‌دسترس ست می‌شود.

## ۱۱. خارج از دامنه (YAGNI)

- کپی/قالب‌گیری برنامه (پیشنهاد آینده)، اشتراک برنامه بین کاربران، ویرایش هم‌زمان،
  برنامه‌های موازی در یک روز، و تاریخ‌wise بودن درصد تکمیل (درصد روی ساختار فعلی است).

## ۱۲. معیارهای پذیرش

- [ ] کاربر عادی در `/programs` برنامه می‌سازد: اسم + روزها + عنوان هر روز + دستهٔ نام‌دلخواه + حرکت از بانک + ست/تکرار.
- [ ] پیش‌نمایش کالری هر حرکت با وزن کاربر درست است.
- [ ] تا ۳ برنامه؛ چهارمی با پیام فارسی رد می‌شود؛ پس از حذف نرم یکی، می‌شود ساخت.
- [ ] ستارهٔ پیش‌فرض، `profiles.program_id` را عوض می‌کند و در «امروز» اعمال می‌شود.
- [ ] انتخاب‌گر «امروز» برنامهٔ خودش + برنامه ادمین را نشان می‌دهد و موقتی جابه‌جا می‌کند.
- [ ] حذف برنامه → لاگ‌ها پاک نمی‌شوند و در گزارش/تقویم/تاریخچه دیده می‌شوند.
- [ ] درصد تکمیل روز، همهٔ حرکت‌ها را می‌شمارد.
- [ ] ادمین همچنان برنامه سراسری می‌سازد (بدون سقف ۳) و به کاربران تخصیص می‌دهد.
- [ ] موبایل iOS: ریزش چیدمان ندارد؛ تست‌ها در CI سبز.
