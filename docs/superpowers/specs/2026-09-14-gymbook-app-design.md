# GYMBook — طراحی نسخه اپ ری‌اکت با Supabase

تاریخ: ۲۰۲۶-۰۹-۱۴ · وضعیت: پیش‌نویس برای بازبینی

## ۱. هدف

نسخه‌ی فعلی یک فایل `index.html` استاتیک روی GitHub Pages است که داده‌ی تیک‌ها را
فقط در `localStorage` همان دستگاه نگه می‌دارد. هدف، تبدیل آن به اپ React است که:

- کاربر/رمز واقعی داشته باشد (لاگین)
- داده‌ها بین گوشی چند نفر هم‌رسان شود (Supabase)
- ادمین بتواند کاربر و برنامه‌ی تمرین شخصی بسازد
- هر کاربر فقط برنامه و گزارش خودش را ببیند
- هر حرکت و هر روز کالری‌سوزی داشته باشد (فرمول MET × وزن)

## ۲. دامنه (فیچرهای مورد‌تایید)

1. نقش ادمین که می‌تواند کاربر جدید بسازد، رمز ست/ریست کند، وزن و برنامه بدهد.
2. بانک حرکات (exercises)؛ ادمین برای هر کاربر «برنامه» شخصی می‌سازد.
3. هر کاربر برنامه‌ی خودش را می‌بیند و حرکات را تیک می‌زند.
4. گزارش و تاریخچه به‌ازای هر کاربر (تقویم ماهانه، استریک، نمودار هفتگی، تاریخچه هر حرکت).
5. شمارنده‌ی کالری برای هر حرکت و مجموع روز/هفته/ماه در گزارش.
6. سید اولیه: سه کاربر **صادق** (ادمین)، **ساغر** و **نازی** با برنامه‌های موجود.
   - صادق → برنامه‌ی قدرتی/عضله‌سازی
   - ساغر و نازی → هر دو به همان برنامه‌ی چربی‌سوزی/کراس‌فیت اشاره می‌کنند
     (چند کاربر می‌توانند یک program_id مشترک داشته باشند؛ نیاز به کپی نیست).

### خارج از دامنه (YAGNI)
- پرداخت، اشتراک، نوتیفیکیشن پوشی، چت، ویدیو، دوربین.
- پلن‌های تمرین چندتایی برای یک کاربر در یک روز (فعلاً یک برنامه‌ی فعال به‌ازای کاربر).

## ۳. پشته‌ی فنی

- React 18 + Vite (JavaScript، بدون TypeScript برای سادگی).
- React Router با **HashRouter** (سازگار با GitHub Pages بدون کانفیگ ریدایرکت).
- TanStack Query برای واکشی/کش داده‌های Supabase.
- Supabase JS SDK v2 (`@supabase/supabase-js`) برای auth و داده.
- Recharts برای نمودار هفتگی.
- vite-plugin-pwa برای «افزودن به صفحه‌ی اصلی» و حالت آفلاینِ خواندنی.
- استایل: منتقل‌کردن CSS تیره و RTL فعلی (فونت Vazirmatn، `dir="rtl"`).
- دیپلوی: GitHub Actions → Build → gh-pages. سایت استاتیک فعلی تا آماده‌شدنِ
  اپ سرو می‌شود و بعد جای خود را به build ری‌اکت می‌دهد.

## ۴. معماری

```
GitHub Pages (static SPA)
      │  HTTPS (publishable key)
      ▼
Supabase  ── Postgres + RLS
   ├── Auth (email + password)
   └── Tables: profiles, exercises, programs, program_days,
               program_items, checks
```

SPA روی کلاینت اجرا می‌شود؛ هیچ بک‌اند اختصاصی نداریم. تنها لایه‌ی امنیت داده،
**RLS** در Postgres است (کلید publishable به‌هرحال عمومی است).

## ۵. مدل داده

### profiles
| ستون | نوع | توضیح |
|---|---|---|
| id | uuid PK | = auth.users.id |
| name | text | نام نمایشی (صادق/ساغر/نازی) |
| role | text | `admin` \| `member` |
| weight_kg | numeric | برای محاسبه‌ی کالری؛ قابل ویرایش |
| program_id | uuid FK→programs nullable | برنامه‌ی فعال کاربر |
| approved | bool | تا ادمین تایید نکند، برنامه نمی‌بیند |
| created_at | timestamptz | |

> یک تریگر روی `auth.users` برای هر اکانت جدید یک `profiles` می‌سازد؛ اگر
> جدول خالی باشد نقش `admin` وگرنه `member` و `approved=false` (بوت‌استرپ ادمین).

### exercises (بانک حرکات)
| ستون | نوع | توضیح |
|---|---|---|
| id | uuid PK | |
| name_fa, name_en | text | |

| met | numeric | شدت MET (اسکات ۵، برپی ۸، پلانک ۳.۵ …) |
| sec_per_rep | numeric | ثانیه‌ی هر تکرار (برای محاسبه‌ی زمان کار) |
| created_by | uuid | سازنده (ادمین) |

### programs
| ستون | نوع | توضیح |
|---|---|---|
| id | uuid PK | |
| title, description | text | |

### program_days
| ستون | نوع | توضیح |
|---|---|---|
| id | uuid PK | |
| program_id | uuid FK programs | |
| day_key | text | `sat`,`sun`,`mon`,`tue`,`wed`,`thu`,`fri` |
| day_label, focus | text | «شنبه»، «بازو» |

### program_items
| ستون | نوع | توضیح |
|---|---|---|

| day_id | uuid FK program_days | |

| reps | int | تکرار در هر ست |

### checks (تیک‌ها / تاریخچه)
| ستون | نوع | توضیح |
|---|---|---|
| id | uuid PK | |
| user_id | uuid FK profiles | |
| date | date | تاریخ محلی تمرین |
| item_id | uuid FK program_items | حرکت انجام‌شده |
| kcal | numeric | اسنپ‌شات کالری در لحظه‌ی تیک |
| created_at | timestamptz | |

قید: `unique(user_id, date, item_id)` — یک بار تیک، یک رکورد؛ برداشتن تیک = حذف رکورد.

> چرا kcal ذخیره می‌شود؟ تا تغییر وزن کاربر در آینده، تاریخچه‌ی قبلی را عوض نکند.
> برای درصدِ تکمیل روز، تعداد آیتم‌های `main` برنامه‌ی فعال در لحظه‌ی نمایش حساب می‌شود.

## ۶. محاسبه‌ی کالری (MET + وزن)

```
work_min = sets × (reps × sec_per_rep) ÷ 60
kcal     = met × 3.5 × weight_kg ÷ 200 × work_min
```

- زمان استراحت حساب نمی‌شود (فقط کار خالص).
- برای حرکات زمان‌محور مثل پلانک/کرانچ: `reps` همان «ثانیه» در نظر گرفته می‌شود و
  `sec_per_rep = 1`، پس `work_min = sets × reps ÷ 60`.
- مقدار `kcal` روی هر آیتم و مجموع روز نمایش داده می‌شود؛ در گزارش جمع روز/هفته/ماه.
- این فرمول تخمینی است و در UI با برچسب «≈» مشخص می‌شود.

## ۷. احراز هویت و دسترسی

- صفحه‌ی `/login` با ایمیل + رمز.
- **بوت‌استرپ:** اولین اکانتِ ساخته‌شده خودکار `admin` می‌شود (صادق).
- **ساخت کاربر توسط ادمین:** پنل «مدیریت کاربران» با `supabase.auth.signUp`
  (با کلید publishable و خاموش‌بودن «Confirm email» در داشبورد) اکانت می‌سازد،
  رمز موقت ۸+ کاراکتر ست می‌کند، و `profile` را `approved=true` می‌کند.
- **کاربر عادی** بعد از ورود می‌تواند رمز خودش را عوض کند و وزنش را ویرایش کند.
- محدودیتِ آگاهانه: چون اپ استاتیک است، ثبت‌نام عمومی با همان کلید باز می‌ماند؛
  اما هر اکانت تازه تا ادمین `approved` و برنامه ندهد، هیچ داده‌ای نمی‌بیند
  (RLS). برای استفاده‌ی خانوادگی/گوشی دوستان قابل قبول است. (کدِ دعوت در نسخه‌ی بعد.)

### نقش‌ها (RLS)
| عملیات | member | admin |
|---|---|---|
| دیدن/نوشتن checks خودش | ✔ | فقط با policy جدا: دیدن همه |
| ویرایش profile خودش (رمز/وزن) | ✔ | ✔ |
| تغییر role/approved/program دیگران | ✘ | ✔ |
| CRUD روی exercises/programs | ✘ | ✔ |
| دیدن گزارش دیگران | ✘ | ✔ |

کمک‌کمک `is_admin()` به‌صورت `security definer` برای پالیسی‌ها.

## ۸. مسیرها و صفحات

| مسیر | محتوا | دسترسی |
|---|---|---|
| `/login` | ورود / ساخت اکانت ادمین اولیه | عمومی |
| `/` (امروز) | برنامه‌ی روز کاربر، تیک حرکت‌ها، نوار تایمر، کالری روز | کاربر لاگین‌شده |
| `/report` | تقویم ماهانه، استریک، نمودار هفتگی، تاریخچه هر حرکت | کاربر لاگین‌شده |
| `/profile` | نام، وزن، تغییر رمز | کاربر لاگین‌شده |
| `/admin/users` | ساخت/ویرایش/حذف کاربر، رمز، برنامه، تایید | ادمین |
| `/admin/exercises` | بانک حرکات (CRUD) | ادمین |
| `/admin/programs` | ساخت‌گر برنامه (روز→حرکت از بانک با ست/تکرار/استراحت) | ادمین |

هنگام ورود، مسیر پیش‌فرض: اگر `approved=false` صفحه‌ی «در انتظار تایید ادمین».
بقیه صفحه‌ی «امروز» روی `day_key` امروز باز می‌شود (همان رفتار `todayIndex` فعلی).

## ۹. سید اولیه

دو بخش، چون بخشی داده است و بخشی رمز:

- **سید الف (امن، داخل ریپو):** بانک حرکات + دو برنامه (قدرتی صادق، چربی‌سوزی
  ساغر/نازی) با روزها و آیتم‌ها، دقیقاً منطبق بر محتوای `index.html` فعلی.
  مقادیر MET و sec_per_rep از جدول استاندارد. اسکریپت `supabase/seed.sql`.
- **سید ب (حساس، فقط در SQL Editor داشبورد اجرا شود، commit نشود):**
  ساخت سه اکانت auth (صادق/ساغر/نازی)، تریگر profile را می‌سازد، سپس
  صادق=`admin`+approved، ساغر و نازی=`member`+approved با `program_id` مشترک،
  و وزن‌ها تنظیم می‌شود. رمز‌های اولیه در چت به کاربر داده می‌شود و
  **باید بعد از اولین ورود عوض شوند** (به‌دلیل عدم commit در ریپوی عمومی).

وزن پیش‌فرض: ساغر ۶۳kg (موجود در متن فعلی)؛ صادق و نازی مقدار اولیه
تخمینی که کاربر در `/profile` اصلاح می‌کند.

## ۱۰. تست

- **Vitest** برای منطق خالص: `calcKcal` (MET/زمان/حرکات زمان‌محور)،
  `computeStreak`، `dayCompletionPercent`، قالب‌اعداد فارسی `fa()`.
- تست سطح کامپوننت با React Testing Library: کارت حرکت (تیک/کالری)،
  پالیسی سمت UI (member صفحه‌ی ادمین نمی‌بیند).
- پالیسی‌های RLS: مجموعه کوئری‌های `supabase` در حالت mock با JWT دو نقش.
- اجرای تست در GitHub Action قبل از دیپلوی.

## ۱۱. امنیت و ریسک‌ها

- کلید publishable عملاً عمومی است؛ تکیه‌گاه امنیتی RLS است، نه مخفی‌بودن کلید.
- رمزها هیچ‌گاه در کد کلاینت یا ریپو نیست؛ فقط در Supabase Auth (هش‌شده).
- سید ب (شامل هش رمز) در ریپو commit نمی‌شود؛ فقط در داشبورد اجرا.
- محدودیتِ ثبت‌نام عمومی (بند ۷) مستند و با `approved` مهار شده.
- `input`ها با escape/markup ایمن ساخته می‌شوند (React به‌طور پیش‌فرض escape می‌کند؛
  برای `how/tip` که HTML ساده دارند از متن بدون dangerously use نمی‌کنیم).
- quota رایگان Supabase: ۵۰٬۰۰۰ کاربر، ۵۰۰MB db — برای چند کاربر خیلی زیاد است.

## ۱۲. معیارهای پذیرش

- [ ] با سه اکانت اولیه وارد می‌شوم؛ صادق پنل ادمین می‌بیند، بقیه نه.
- [ ] نازی دقیقاً همان برنامه‌ی ساغر را می‌بیند.
- [ ] تیک حرکت روی یک گوشی، همان روز روی گوشی دیگری هم نمایش داده می‌شود.
- [ ] هر حرکت و مجموع روز، کالری تقریبی نشان می‌دهد.
- [ ] صفحه گزارش: تقویم ماهانه با درصد تکمیل، استریک، نمودار هفتگی، تاریخچه حرکت.
- [ ] ادمین کاربر جدید می‌سازد، رمز می‌دهد، برنامه تخصیص می‌دهد.
- [ ] موبایل iOS: بدون ریزش چیدمان، safe-area رعایت، «افزودن به صفحه اصلی» کار می‌کند.
- [ ] تست‌ها در CI سبز و قبل از دیپلوی اجرا می‌شوند.

## ۱۳. مراحل اجرا (خلاصه — پلن کامل در گام بعد)

1. اسکلت Vite + React + Router + PWA + Supabase client + انتقال CSS فعلی.
2. طرح‌نویسی schema + migrationها + تریگر پروفایل + `is_admin()` + RLS.
3. Auth flow (ورود/خروج/بوت‌استرپ) + Context نشست.
4. صفحه «امروز» (نمایش برنامه، تیک، تایمر، کالری).
5. گزارش‌ها + موتور محاسباتی (تست‌محور).
6. پنل ادمین: کاربران، بانک حرکات، ساخت‌گر برنامه.
7. سید الف (داخل ریپو) + راهنمای اجرای سید ب.
8. CI دیپلوی + حذف تدریجی سایت استاتیک.
